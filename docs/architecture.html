01 — Premise

The thesis: the generation step is the easy half

Most “AI for testing” demos stop at the model wrote some tests. SpecForge is built around the three problems that start immediately afterward.

The project exists to answer a question that a test-generating demo never has to face: when a generated test fails, why did it fail? There are three candidate explanations — the model wrote a bad test, the service has a real bug, or the environment drifted — and if you can't tell them apart, the suite is worthless as a regression gate.

Three concrete problems follow from that:

  • Non-determinism. An LLM asked the same question twice may answer differently. A suite that changes between runs can't gate anything.
  • Flakiness attribution. When a test fails intermittently, teams burn enormous time deciding whether to blame the test, the service, or the environment.
  • Traceability. In regulated environments “we have tests” is insufficient; you must show which requirement each test covers. This comes directly from FDA-regulated medical device work, where design controls demand demonstrable requirement-to-test linkage.
The organizing principle

Confine non-determinism to exactly one boundary, and make everything around it boringly reliable. The LLM emits structured data validated against a strict schema; every downstream stage is deterministic templating and assertion. That single decision is what makes failure attribution possible later — and nearly every other decision in the project is downstream of it.

03 — Structure

Repository architecture: two deployables, one contract

The repo holds two genuinely separate programs. Keeping them separate is not tidiness — it is what makes the target controlled, which is the premise the whole project rests on.

Why the separation earns its keep

If both installed one flat requirements.txt, you'd be asserting they share a runtime. They don't — and pretending otherwise leaks the tool's dependencies (the Anthropic SDK, for one) into the environment that is supposed to be a clean, predictable target. The README's central claim is that a controlled target makes every failure unambiguous; a leaky dependency boundary quietly undermines exactly that.

The version-pinning styles differ for the same reason: target_api is an application you run, so it pins exactly (==) for reproducibility; specforge is library-shaped, so it floats (>=) for flexibility.

04 — Core mechanism

The validated boundary, precisely

This is the part worth understanding in detail, because it is both the project's best idea and the source of its most instructive bug.

What the model actually emits

The generator does not ask for code, or for free text that gets parsed. It asks for a TestSuite — a Pydantic model — using structured outputs, where the API constrains the response to a strict JSON schema. Each TestDefinition carries: an id, a description, a case_type, a spec_ref, the HTTP method and path, an auth role, request payloads, and the expected status.

Two guarantees that are easy to conflate

A design pillar that had to be retired

The README originally claimed “temperature 0 and schema validation on every generation call.” The temperature half no longer exists. Sampling parameters (temperature, top_p, top_k) are removed on current Claude models and return a 400; the old config named a legacy model, which is why it hadn't broken. Even where accepted, temperature=0 never actually guaranteed identical output.

So the structural guarantee now rests entirely on the schema — and the honest architecture measures stability rather than assuming it. This made the thesis stronger, not weaker.

Where the boundary validates, in two stages

Request payloads (body, path_params, query_params) are JSON strings on the wire, not objects. That looks like a downgrade and is actually a forced move — see §06. The consequence is that validation happens twice at the same boundary:

  1. The API guarantees the response matches the schema — the field is a string.
  2. A Pydantic validator guarantees the string parses as a JSON object — the string is usable.

Downstream code never parses by hand; it calls body_dict(), path_params_dict(), or resolved_path(), which substitutes path template parameters and returns a concrete URL.

05 — Rationale

Decisions and what each one cost

Every choice below has a real trade-off. Being able to name the cost is what separates understanding the design from reciting it.

Build the target service instead of testing a public API

A controlled target allows deliberately tricky validation, a planted flaky endpoint to prove the detector works, and fully offline runs with no rate limits or third-party noise. Against a public API, every failure is ambiguous.

Cost: an entire phase of work before the actual tool began, and results that don't automatically generalize to messier real-world APIs.

The LLM emits structured data, never code

Generation returns validated JSON; rendering to pytest is deterministic templating. The non-deterministic component is confined to one auditable boundary instead of producing arbitrary executable output.

Cost: the renderer can only express test shapes the schema anticipated. Novel cases need a schema change, not just a better prompt.

Tests run on SQLite; production runs on Postgres

The same application code serves both because the database is injected via a DATABASE_URL config seam. Tests get a disposable file deleted on setup — hermetic, instant, no external service.

Cost: SQLite and Postgres are not behaviorally identical, so the suite can miss Postgres-specific bugs.

Mock the Claude call in CI

The tool's 10 tests verify validation and error handling with an injected fake client. CI needs no API key, costs nothing, and can't fail because of a network blip.

Cost: CI proves the plumbing works, never that the prompt is any good. Generation quality needs separate, deliberate evaluation.

Keep the smoke script and the pytest suite

smoke_test.py is a top-to-bottom narrative you run by hand to see the service breathe. The pytest suite is a machine-enforced gate with per-test granularity. Same behavior, two audiences.

Cost: two artifacts covering similar ground can drift apart if only one is maintained.

Make spec_ref a required field

Every test must name the spec element that motivated it. Phase 6's traceability matrix is therefore designed in from the first line rather than retrofitted — the requirement that comes straight from regulated-software design controls.

Cost: the model must justify every test, which may suppress a useful test it can't cleanly attribute.

extra="forbid" on the schema

Unknown fields are rejected outright, so a model that starts emitting a new key fails loudly instead of having it silently dropped.

Cost: brittleness by design — a harmless additional field breaks the run rather than being ignored.

Declare pythonpath rather than package the app

The import failure could have been fixed by making target_api a proper installable distribution. One config line states the only fact that is true today, with zero structural commitment.

Cost: deferred work. The moment anything needs to import the target as a library, the packaging cost arrives.

Delete dead code instead of finding it a use

An unused require_admin dependency was removed rather than given a route. The endpoint surface is the generator's input — every route added is more surface the tool must model, test, and diagnose.

Cost: one authorization dimension (role-gated regardless of ownership) is now untested, because the service genuinely doesn't have it.

Document response codes in the service itself

FastAPI only infers 2xx and 422. Explicit responses={...} declarations make 401/403/404/409 visible in openapi.json, so the generator can see the permission model at all.

Cost: the contract is now maintained by hand alongside the code, and can drift from actual behavior.

Defect 1 — the schema was under-specified

Every payload field was declared as a free-form dict. That renders as an object schema with no properties; structured outputs cannot populate it, so the model was constrained to emit {} every single time — and complied exactly. A test labelled “valid create → 201” carried an empty body.

The lesson worth carrying

A strict schema guarantees shape, not usefulness. “Structurally valid and semantically empty” passes every validation gate cleanly. Validation is necessary and nowhere near sufficient — which is the sharper, empirically-backed version of the project's own thesis.

Defect 2 — the spec was lying by omission

The generator can only be as good as its input, and openapi.json turned out to be a lossy projection of real behavior. Two consequences:

  • Only 2xx and 422 were documented, so the permission model was invisible. The model guessed 404 for cross-user access — a reasonable REST convention — where the service actually returns 403. Those tests would have failed against correct behavior. Admin got zero coverage because roles never appeared in the spec.
  • The headline unit-dependent range serialized as a bare "type": "number". The Pydantic model_validator enforcing it does not reach OpenAPI, so the target's signature validation rule attracted no boundary tests at all.

The payoff, once the spec described the rule

Both defects were the same bug wearing different clothes: an under-specified contract silently produces confident, useless output. Once from the Pydantic schema, once from the OpenAPI spec. Neither failed loudly; both passed every gate in place at the time.

07 — Behavior

How the pieces interact

Identity is expressed as a role, not a credential

A test says auth: "other_user", never a token. The four roles — none, user, other_user, admin — let the generator reason about authorization semantics while the executor owns credential mechanics. This is why the model can express “a different user must not read this” without knowing anything about JWTs, and why the executor can change its auth strategy without regenerating a single test.

Paths stay templated until execution

A test carries path: "/readings/{reading_id}" plus path_params: '{"reading_id": "1"}'. Keeping them separate preserves the link to the spec — spec_ref refers to the templated path — while resolved_path() produces the concrete URL at execution time. Collapsing them early would destroy the traceability the project is built to demonstrate.

Configuration is the seam that decouples code from environment

DATABASE_URL is read once in config.py and consumed in database.py; nothing else in the app knows which database it is talking to. The test conftest.py sets that variable before the app imports, which is the entire mechanism behind hermetic tests. Same pattern, one layer up: CLAUDE_MODEL is read from the environment, so the generator's model is a deployment decision rather than a code change.

The failure modes the generator handles explicitly

Because structured outputs removes malformed JSON from the space of possible failures, only two remain, and both are checked before the suite is read: the model declining the request (stop_reason == "refusal"), and the response hitting the token ceiling mid-suite (stop_reason == "max_tokens"). Both raise a typed GenerationError that the CLI turns into a clean message.

08 — Verification

Testing and CI

Two independent jobs, each across Python 3.11 and 3.12 — four runs total. The two halves of the repo are verified separately because they are separate programs.

CI topology. Neither job requires an API key.

A trap worth knowing

CI invokes bare pytest, which — unlike python -m pytest — does not put the working directory on sys.path. A suite that passes locally under -m can fail in CI with ModuleNotFoundError. Both pyproject.toml files set pythonpath = ["."] to close the gap. When verifying locally, run it the way CI does.

The testpaths setting in each config keeps the two suites from colliding, and deliberately excludes smoke_test.py — a manual narrative script, not a pytest module.

09 — Honesty

Known debt

Carried deliberately at this size, and worth naming before someone else names it.

Admin fixture writes to the DB There is no API to mint an admin, so the test promotes a user directly — coupling a test to the persistence layer. Acceptable; revisit if the User model changes.
Generation quality is unmeasured CI proves the plumbing, never the prompt. There is no eval telling you whether run N is better than run N−1. Phase 4 — the flake detector is the first real measurement.

10 — Delivery

Explaining it out loud

Answers to the questions this project invites. The specifics are what make it credible — lead with them.

“What does it do?”

It takes an OpenAPI spec and produces a runnable pytest suite covering positive, negative, boundary, and authorization cases — then runs that suite repeatedly in CI, identifies which tests are non-deterministic, and clusters failures into likely root causes. The generation is the least interesting part; everything downstream of it is the point.

“Why not just let the model write the tests?”

Because then you can't tell why a test failed. If the model writes arbitrary code, a failure could be a real bug, a bad test, or a hallucinated API call — and you have no way to separate them. Constraining the model to emit structured data against a strict schema means the only thing it can get wrong is test design, which is the thing you actually want it deciding.

“How do you handle non-determinism?”

I separate two things people usually conflate. Structural determinism — that the output is always a valid test definition — is guaranteed by the schema. Semantic stability — that the same spec yields the same tests — is not guaranteed, and I don't pretend it is; it gets measured across N runs. I originally claimed temperature 0 gave me determinism; that turned out to be wrong twice over, because sampling parameters are removed on current models and never guaranteed identical output anyway.

“What's the most interesting thing you found?”

The first live run generated 47 structurally perfect tests, every one of which was unexecutable — all the request bodies were empty. The cause was my own schema: a free-form dict renders as an object with no properties, which structured outputs cannot populate, so the model correctly emitted {} 47 times. It taught me that a strict schema guarantees shape, not usefulness — “structurally valid and semantically empty” passes every gate you have.

“What did that lead you to change?”

Two things. Payloads became JSON strings validated in a second stage, so the boundary still validates but in two steps. And I discovered the same bug in the other direction: my OpenAPI spec was a lossy projection of real behavior — it documented only 2xx and 422, so the generator guessed 404 where the service returns 403, and never tested the unit-dependent range because that rule didn't survive serialization. I made the service describe itself honestly, and the very next run probed all four range boundaries correctly.

“Where does the regulated-software background show up?”

spec_ref is a required field on every test. In FDA-regulated device software, design controls demand demonstrable requirement-to-test linkage — “we have tests” doesn't satisfy an auditor. So traceability is a schema-level guarantee from the first commit, not a report generated at the end. If a test can't name the spec element that motivated it, it doesn't validate.

“What would you do differently?”

I'd write the schema against the actual constraints of structured outputs before writing the prompt — the empty-payload bug was a day of debugging that a five-minute read would have prevented. And I'd have made the target service describe itself accurately from the start; I built deliberately tricky validation and then shipped a spec that didn't mention it, which meant the tool couldn't see the one thing it was built to find.
